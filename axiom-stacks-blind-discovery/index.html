Does Axiom's Stacks library help an AI agent find proofs faster? A quick test

ethduke · 5 November 2026 · about a 6-minute read

TL;DR

  • On the one problem that needed a theorem Mathlib doesn't have, the agent found it in Axiom on its own and finished about 3.4× faster (39 s instead of 133 s) and about 74% cheaper.
  • On the two problems Mathlib could already handle, it ignored Axiom and nothing changed.
  • This is a quick, small test: 33 runs, about $3 at API prices. The search was easy, and these problems are far from what a library like this is really for.

On 4 November, Axiom released a Lean formalization of the whole Stacks Project, the big open reference for algebraic geometry. It's about 63,000 files (Axiom says 16 million lines), built on Mathlib, mostly written by AI agents and checked by Lean.

Axiom pitches it as infrastructure. Researchers and AI agents can import its definitions and theorems into new proofs instead of rebuilding them, and the longer-term hope is that people and agents explore new mathematics on top of it.

That bigger promise is hard to test in an evening, so I asked a much smaller question: if I hand an AI agent the whole library and don't tell it where to look, does it find the theorem it needs, and does it reach a verified proof faster than with Mathlib alone?

A sloppy first try

My first attempt, the evening of the release, made things too easy for the library. I told the agent which file to open, made only two small Axiom files available, and on the hardest problem asked it to prove the very theorem that sat in one of them. Of course, importing the answer was faster than proving it (4.4×). The smaller differences on the other problems were within run-to-run noise. So I set up a fairer version.

The setup

Same agent (Codex with GPT-6.1 Sol, high reasoning effort), same three problems, three setups:

  • Mathlib only: the agent can't see Axiom at all.
  • Axiom, no hints: Mathlib plus all 62,972 Axiom files. The prompt doesn't name any theorem or file.
  • Axiom + file name: the same, plus the name of the Axiom file and theorem that would help. Comparing this with the no-hint runs shows what searching cost.

The problems were small corollaries of known results:

  1. If a ring has no idempotents other than 0 and 1, every locally constant Boolean function on its prime spectrum is constant.
  2. For a finitely generated idempotent ideal I, the prime spectrum splits into the zero locus of I and its complement.
  3. If every localization at a maximal ideal is Noetherian and every nonzero element lies in only finitely many maximal ideals, then every quotient A/I is Noetherian.

The first two are easy with Mathlib. The third needs a result Mathlib doesn't package.

To keep it honest, every run started fresh with no web access, the problems and run order were fixed (and hashed) before anything was scored, and Lean had to accept a proof of the exact statement. The details are at the end.

What happened

On Task 3, all five no-hint Axiom runs finished before the fastest Mathlib-only run: a median of 38.6 s against 132.8 s. With five runs each, a split that clean would happen by chance about once in 126 tries.

On Tasks 1 and 2, nothing changed. The medians are within 0.3 s of each other, and the Axiom runs didn't use Axiom at all: Mathlib already had what they needed, and the agent found it there.

The one problem where it mattered

Both agents started with the same search, for "finite character". Mathlib had nothing. In Axiom it hit StacksFrontier/RingTheory/Noetherian/FiniteCharacter.lean, which proves Nagata's criterion: a ring is Noetherian if its localizations at maximal ideals are Noetherian and every nonzero element lies in finitely many maximal ideals. That's exactly what Task 3 needs.

The agent combined it with Mathlib's fact that quotients of Noetherian rings are Noetherian, and Lean accepted the first attempt:

letI : IsNoetherianRing A :=
  isNoetherianRing_of_localization_maximal_of_finite hloc hfin
intro I
infer_instance

Without Axiom, the agent rebuilt the whole argument by hand. In numbers, for Task 3:

  • 3.4× faster: 38.6 s instead of 132.8 s
  • about 74% cheaper: $0.05 instead of $0.19 per proof
  • 0 failed compiles instead of 10, across five runs each
  • 13-line proof files instead of 52–84 lines

That's about 94 seconds and 14 cents per proof. Small in absolute terms, but it shows the pattern: when the library has the missing piece, the agent can find it and use it. All of it came from one file: 98 lines and two theorems, importing only Mathlib.1

Telling the agent the file name saved another 11 seconds or so, so at least here, searching 63,000 files was cheap.

Cost tells the same story. Total token counts can mislead, though, because the agent re-sends its whole conversation every turn and most of that is cached. On Task 2, the Axiom runs sent 31% more tokens but 40% fewer fresh ones, so they still came out 22% cheaper.

What this doesn't tell us

Quite a lot. A few things to keep in mind:

  • The search was easy. The problem says "finite-character", the file is called FiniteCharacter.lean, and the problem's hypotheses are copied from that theorem. Both agents searched for that phrase first. Real problems won't come phrased in the library's own words.
  • It's one theorem. All of the benefit comes from one 98-line file, and I picked this problem after my first try showed that theorem mattered.
  • These are tiny, known results. Mathlib alone always got there in under three minutes. None of these problems touches what the Stacks Project is really about (schemes, stacks, cohomology), and none of it is new mathematics. The library's real test is whether agents can build something new on top of it, and this doesn't measure that.
  • Small numbers: three to five runs per setup, one model, one laptop.
  • Correctness isn't the issue. The Axiom theorem used here was written by AI and hasn't been reviewed by people yet, but Lean checked every proof, and every problem is stated using Mathlib's own definitions.

What I'd try next

  • Reword the prompt. Run Task 3 again without the phrase "finite-character" and with the hypotheses renamed and restated. It costs about $1.50. If the agent still finds the theorem, the discovery result holds.
  • Go deeper. Use problems from the parts of the Stacks Project Mathlib doesn't cover, where Mathlib alone usually fails, and count how many get solved rather than how fast.
  • The real question: give agents results that aren't in either library and need its deeper parts, and see whether having the library changes what they can prove at all.

How it was run
  • Versions: Axiom Stacks commit f8e70c5dd04bfabcb423d5e325461f527c85a5d6; Mathlib 16edf57de7933555826307a3d81b4391a3657a09, the revision Axiom builds against; Lean v4.34.0-rc2; macOS on Apple silicon.
  • Agent: gpt-6.1-sol through codex exec, high reasoning effort. Each run was a fresh session in a fresh directory with no memory, no web tools and no network access, limited to 600 s, 3 million tokens and 80 tool calls. I scanned all 1,042 tool calls afterwards: none used the network.
  • Fairness: prompts were identical within a setup, and the Axiom and Mathlib-only prompts differed in one line, which lists the available libraries. Problems, budgets, scripts and a shuffled run order were frozen and hashed before the first scored run. After two rounds of Task 3, I added two more runs per setup; the three planned rounds alone give the same 3.4× ratio.
  • Checking: a proof counted only if Lean compiled it, it proved the exact frozen statement, and it used only Lean's three standard axioms. Every final proof was rechecked independently. Each problem was proved once with Mathlib alone beforehand.
  • Timing: from the prompt to the end of the Lean check, so it includes Lean start-up (roughly 10–20 s per check). About 18 minutes of setup is excluded.
  • Cost: estimates at published API prices ($2 per million uncached input tokens, $0.10 cached, $10 output), not an actual bill. All 33 runs together came to about $2.85.
  • Statistics: medians and ranges, plus exact permutation tests for the two Task 3 comparisons. With three to five runs per setup, these describe this sample, not a general effect.
  • Data: prompts, proofs, session traces and scripts are available on request through GitHub.
